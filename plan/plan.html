Foundation — the delay scale

One colour scale, reused on the dot, in the search list and in the timeline, so a colour always means the same thing. Delay comes from the trip's resolved delay in seconds, which is usually the next stop’s arrivalDelay but is not simply read off it: on a SCHEDULED stoptime that field is 0 and means no data, not on time, so a train with no realtime, or one past the border where MÁV stops publishing it, would otherwise render green. The full resolution order, including carrying a border delay forward as “+53 min at Hegyeshalom”, is in SPEC.md §7.2.

Type colour (the middle ring)

Always from the response: trip.route.textColor, a bare hex string such as 274F96 that needs a # prefixed. There is no category lookup and nothing about train type is hardcoded.

textColor is effectively guaranteed, so the fallback is deliberately not a plausible-looking colour: a null falls back to pure white, which reads as a broken marker against every basemap. If you ever see a white ring, the data is wrong and you notice immediately instead of being quietly lied to.

normal  ·  null textColor

Ring stack — thinner type ring

Delay fill · 1.6 px black · 1.4 px type colour · 1.4 px black. The type ring is now the thinnest band in the stack — a hairline accent rather than a second body colour — so the delay fill, the thing you actually scan for, keeps the pixels. Inner black keeps a red delay off a dark-red type colour; outer black is the map contrast ring. Ø 24 px on a 52 px canvas, which exists so the wedge stays inside it at every rotation — not as a hit box. Only the painted marker is hoverable.

Behaviour common to all three

ConcernRule
MovementRotation and position both tween over ~450 ms between 30 s polls so trains glide rather than teleport, each on its own inner element (.rot and .mv) so neither fights Leaflet's own transform on the marker root. heading is always honoured, including at speed === 0 — a stationary train still faces a direction. It is normalised first: the feed returns negative and fractional values. Not stretched across the full 30 s: that would park the marker at a position MÁV never reported. See SPEC.md §3.
ZoomNo zoom-dependent variants. The marker is identical at every zoom. An earlier draft collapsed to a plain dot below z8; dropped, because it was the only thing that would have forced setIcon().
Hit areaOnly the painted marker is hoverable: pointer-events:none on the <svg>, visiblePainted on the rings and wedge. The 52 px canvas is there so the wedge stays inside it at every rotation, not as a hit target.
ArrivedA train that has reached its terminus stays on the map for 10 minutes and keeps its delay colour, the delay it finished with, so the scale means the same thing on the map, in the search row and in the panel. Arrival is carried by the panel and the hover card's Arrived row, never by draining the marker. A terminal state, not the per-train staleness state the error section rejects.
Route lineSelecting a train draws trip.geometry as a polyline in the type colour, plus a dot at every calling point from stoptimes.stop.lat/lon, coloured with the same past / now / future tokens as the timeline so the map and the panel say the same thing. The marker is never snapped onto the line and never animated along it — it sits where MÁV says it is and glides between fixes like every other marker, because snapping would move it to a position the feed never reported. The other markers are not dimmed and keep full opacity. Geometry is fetched once per published row, not once per trip (measured 18 Aug 2026, plan/findings.md): one call per leg on a merged multi-leg trip, keyed by each leg's suffixed raw id, because the canonical id returns the unsuffixed leg alone and on 351 DRÁVA that is the foreign half; and one per portion on a portioned train, each of which returns the whole journey from the origin, so the shared trunk is trimmed on an exact longest common prefix. Several polylines, never joined, because joining them would draw a chord across a gap that has no track. See SPEC.md §1.
ImplementationL.divIcon holding the inline SVG; heading applied as rotate() on the inner <g> only, so the card anchor never rotates. Markers are keyed by canonical trip id, not vehicleId, which is not unique in a response.

2. Search field — 3 designs

Two sources. The map's own trains, and vagonweb.cz, which knows every train in the 2026 timetable whether it is running this minute or not. Try 929 (on the map and on vagonweb), 849 or 1972 (not on the map, vagonweb has them), kék, deli or sav. A vagonweb row opens the composition, section 4b, and the mock below the three designs shows what that looks like on both platforms. Design B rests on Current, so press Vagonweb or Both there to see the second source. The rows are real, captured from razeni.php on 12 Aug 2026.

All three designs are live. move, Enter selects, Esc closes, Home/End jump. Matching works with or without Hungarian accents (füred ≡ fured ≡ fűred) over train number, route name, category and headsign. At most 5 results are shown; more scroll.

Pressing a vagonweb result opens the composition

A live row flies the map and opens the detail panel. A vagonweb row cannot do either, because the train it names may not be running today, may not be running this month, and has no position, no delay and no next stop. What it does have is a composition. So that is what it opens, and it opens the same card section 4b specifies, with one difference: nothing is selected behind it. Press any vagonweb row in the three designs above and this pair redraws.

Mobile is the case worth designing. There, 4b's composition is a page of the detail panel, reached by swiping across from the route. Opened from a search there is no route to swipe back to and no train to close back onto, so: no pager dots, and the back button returns to the search, not to a panel that was never opened. Everything else, the vehicle list included, is the same component.

    Searching vagonweb — the rules

    ConcernRule
    The requestGET razeni/razeni.php?rok=<year>&jmeno=<query>, proxied through app/api/vw-search and parsed server-side. This page needs no Referer, unlike vlak.php, which is why it can sit behind a search field at all. Full detail in plan/vagonweb.md.
    When it firesNot on every keystroke. Debounced 400 ms, minimum 2 characters, one request in flight at a time and the previous one aborted, answers cached for the session under the folded query. vagonweb is a volunteer site and the local list costs nothing, so the live results are drawn immediately and the vagonweb group lands when it lands.
    What it matchesvagonweb matches jmeno against the number and the train name, and nothing else. Not the route: győr returns nothing there, though it returns live trains here. Number matching is a substring, so 92 matches 929 and 1921 alike.
    The operator filterA number is a number all over Europe. 929 returns seven rows: SNCB, GySEV, MÁV, DB, ČD, SNCF and WESTbahn. Keep MÁV, GySEV, ÖBB and RegioJet, the last under both codes it files with, RJ and RJSK, and drop everything else silently. The dropped rows are not results and are not counted at the user: how many trains numbered 929 exist in Belgium is not a fact this map owes anybody. Match zeme case- and accent-insensitively, the same folding the query gets, so ÖBB and obb are one operator.
    Duplicate rowsNormal, and not a bug to clean up. A jointly run train is filed once per operator (GySEV IC 929 and MÁV IC 929 are both real and differ by one stop), and one number can be filed under two categories (Ex 849 and IC 849, the Balaton summer). Both rows are shown, because they are two different compositions.
    VolumeA full number returns a handful of rows. A name or a fragment does not: Savaria returns 24 and Tópart 48, and the page holds 150 rows before it paginates. Only ever fetch page 1, draw six, count the rest. Never follow &s=2.
    OrderingLive rows first, always, whatever the scores. A train you can watch move beats a timetable entry for the same number.
    FailureThe vagonweb group carries its own error, in its own heading, and never takes the live results down with it: vagonweb search failed. 503 Service Unavailable. with a Retry control beside it. It does not count down and does not retry itself: the 0:02 to 0:30 ladder is the /api/vehicles poll's alone, because vagonweb is a volunteer site on a one-request-per-train-per-day budget. The local list is unaffected and stays interactive. See §5.

    Autocomplete rules (identical in all three)

    ConcernRule
    IndexRebuilt each poll from tripShortName (number + name + category), tripHeadsign and route.longName, folded through an explicit Hungarian accent map (á é í ó ö ő ú ü ű). Both index and query are folded, so accented and unaccented input both match, and the folding is length-preserving so the <mark> offsets stay valid.
    RankingExact number > number prefix > word start in the name > substring anywhere. Ties broken by distance from map centre. At most 5 rows are visible; the rest scroll. Results are computed when the query changes and only then: panning does not re-rank, and a poll refreshes the delay in a row without reordering it.
    Keyboardrole=combobox + aria-activedescendant; the input keeps focus, the list never takes it. One running index across both groups, so the arrow keys cross from the live rows into the vagonweb ones without noticing the heading between them, which is not an option. Enter flies to the train and opens the panel on a live row, and opens the composition on a vagonweb row.
    Empty / no matchEmpty query gives the 5 nearest trains to the viewport centre and asks vagonweb nothing. No match anywhere shows “No train matches …” plus a note that says which sources were asked. A match on only one source is not a no-match: the whole point is that “not on the map” and “does not exist” are different answers.
    PlacementDesktop: top-centre, floating clear of the map's top edge, results dropping down beneath it. The composition card is bottom-left and the toast bottom-centre; when those two would overlap on a narrow window the toast shifts right of the card rather than sitting over it.
    MobileThe full width of the screen minus a margin, at the top, so the input, the three pills and the result rows all have room on a narrow phone. Still a floating card with its own corners and shadow, not a bar welded to the screen edge. List capped to viewport height − keyboard; enterkeyhint="search"; tapping a result blurs the input first so the map is not hidden.

            4b. Carriage composition — 3 designs

            Which coaches the train is actually made of, from vagonweb.cz: the planned composition for the current timetable window, plus the three most recent days someone reported what really ran. The detail panel is a 420 px right sidebar, so on desktop this is a separate card floating at the bottom-left of the map, clear of it; on mobile the panel is the whole screen, so this is its own page, one swipe across, with the train running down the screen instead of across it. That placement is the same in all three designs below. All three designs use the same data and vagonweb's own vehicle drawings, and differ only in how much of a coach they show at once. Every vehicle here is the real drawing; the SVG silhouettes from the first draft are kept as the fallback for the vehicles vagonweb has no drawing for, which the 31 July and 28 July compositions in design C both hit.

            The data path lives in plan/vagonweb.md

            vagonweb has no API, but it does have a server-rendered page, and one GET of it carries every planned composition for the train plus the newest three reported days. It is filtered by operator and category, which the site's own AJAX endpoints are not, so this is both the simpler request and the more precise one. Two catches: it only answers if the request carries a Referer, and the category has to be right. The URL, the four inputs, how the number and name come out of tripShortName, the category map, railjets, route sections, caching and mirroring: all of it in plan/vagonweb.md, verified against the live site on 2 and 4 Aug 2026 and against plan/data-2026-08-04.json.

            What stays below is the design: what a composition looks like, how the difference against the plan is computed and worded, and what the card does when there is nothing to show. The only thing this section adds to the GraphQL query is route.agency { id name }.

            Settled, and it is why this is one request. The page gives three reported days and the designs below draw three. A fourth would need a second call that returns the entire remaining history with no way to limit it, around 200 KB. Three answers "is this train what the timetable says this week?", so the whole section is a single GET with no paging and nothing to merge.

                    The difference against the plan — the whole algorithm

                    Every mark on a vehicle and every word of the sentence comes out of this one function. It is written out in full because getting it wrong is invisible: a mis-paired coach still renders, it just lies.

                    0. Diff against the right plan. A train has one planned composition per timetable window, so a reported day is compared against the window that contained that day, never against today's. Get this wrong and everything below is computed correctly against the wrong baseline: all twenty of 849's reported days fall in May and June, so against its summer plan every one of them reads A different train entirely. See the box above the designs.

                    1. Pair on the car number, never on position. vagonweb prints a number on every coach (span.raz-cislo) and it is the number written on the coach itself, so it survives re-ordering, substitutions and a train running short. Position pairing does not: one substituted coach shifts everything behind it and the whole tail reports as changed.

                    slot(v, i) =
    v.isLoco  ?  (i === 0 ? -1 : 1000 + i)   // a leading loco sorts first,
                                             // a rear or banking loco last
  : v.number  ?  Number(v.number)            // 409, 410, 411 ...
  :              500 + i                     // no number: out of the numbered
                                             // range, still stable

                    2. Pair on the slot, but draw in the reported train's own order. Each slot yields exactly one outcome, which is what makes it impossible for a single coach to be reported twice:

                    Slot is inVehicle kindOutcomeVehicle drawnClause
                    bothsameunchangedreported, no marknothing
                    bothdifferentchange, amber outlinereported411 Apee in place of Apmz

                    "Vehicle kind" is the coach type (Byee, Apmz) or, for a locomotive, loco <class>. Nothing else is compared: a coach that kept its number and type but gained Wi-Fi is not a difference. A slot vagonweb fills with either of two machines matches either of them, so 849 turning up behind its 490 on 9 June is the plan and not a substitution.

                    Order is not the slot order. An earlier draft sorted the result by slot ascending, which quietly assumed car numbers always climb from the front. They do not. A car number is fixed to the coach, and which end of the train it is at depends on which way the train is facing, so the same set reads 21 to 27 on the outward run and 27 to 21 coming back. RJX 63 arrives in Budapest with 27 at the front; sorting by number drew it backwards under a heading that says FRONT OF TRAIN. So never sort by the number. vagonweb hands each composition over head to tail and already knows the direction, so the strip renders it in the order it came in, and the numbers are left to run whichever way they run. A planned vehicle that did not run is put back in the gap it left: directly after whichever vehicle it followed in the plan, or at the head if it was the first thing in it. The sentence is built from the same array, so the words follow the train the same way.

                    3. Render that array twice, in the same order. The strip draws it left to right, so a missing vehicle appears in its own numbered slot rather than at the end. The sentence walks the same array, merging neighbouring vehicles that carry an identical outcome into one clause (409 and 410 Byee missing), then joins the clauses with commas and a final "and", capitalises, and adds a full stop. An empty array gives the fixed string Runs exactly as planned.
